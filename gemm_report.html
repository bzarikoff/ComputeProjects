01Goal & hardware

The investigation started from a plain triple-nested-loop matrix multiply and iteratively optimized it — first on CUDA cores (shared memory, register tiling, multi-level warp tiling), then switching to Tensor Cores with mixed FP16/FP32 precision — while measuring against cublasSgemm as the practical ceiling at every stage. Every result below is at N=1024 on the same GPU, correctness-verified against a CPU reference at N≤512.

02Methodology

01
Naive kernel

One thread per output element; every thread re-reads a full row of A and column of B from global memory. Establishes the correctness baseline and the number to beat.

2070 GFLOPS
02
Shared-memory tiling

Each block cooperatively loads a tile of A/B into __shared__ memory once, reused by every thread in the block instead of hitting global memory per element.

2699 GFLOPS
03
Register (thread) tiling + tile-size sweep

Each thread accumulates TM=4 output rows in registers instead of one, reusing each shared-memory read across multiple FMAs. Swept TILE_SIZE ∈ {8, 16, 32} to find the occupancy sweet spot — see Section 04.

5800 GFLOPS (TILE_SIZE=16, best)
04
Multi-level (block → warp → thread) tiling

Added an explicit warp-tile layer between the block and thread levels, decoupling block shape from tile shape. On CUDA cores alone this reorganized indices without adding new reuse — see Finding 3.

5592 GFLOPS (best config, ≈ flat vs. step 03)
05
Tensor Cores (FP16×FP16→FP32)

Replaced the manual thread-tile accumulation with wmma::mma_sync — a warp-collective 16×16×16 matrix instruction on dedicated hardware. Inputs cast to FP16; accumulation stays FP32.

8224 GFLOPS
06
cp.async double buffering

Two shared-memory buffers instead of one: the next tile loads asynchronously in the background while Tensor Cores compute on the current tile, instead of load → sync → compute → sync running fully serially.

13,358 GFLOPS — final result

04Occupancy investigation

Before adding warp-level tiling, the register-tiled kernel (TM=4) was swept across TILE_SIZE ∈ {8, 16, 32} — the value that sets both the shared-memory tile size and the block's thread count. TILE_SIZE=16 won at 5800 GFLOPS, beating both its neighbors (4025 and 5021 GFLOPS). The charts below explain why, using each tile size's actual measured register count (via nvcc -Xptxas -v) and this GPU's real resource limits.

Resident warps admitted, by limiting resource

Each line = how many warps would fit under that ONE resource alone. The lowest line at a given TILE_SIZE is the actual binding constraint. Shown in warp terms (not raw block count) because raw block count is misleading on its own — small tiles admit many thin blocks, large tiles admit few fat ones.

Resulting occupancy

Occupancy = (blocks admitted × warps/block) / 48 max warps per SM. Red dots mark the three TILE_SIZE values actually compiled and benchmarked.

Formulas

T = TILE_SIZE. All block-count terms are floored — a block only admits if it fully fits.

// max blocks admitted under EACH resource alone bThreads(T) = floor( threadsPerSM / threadsRounded(T) ) bRegs(T) = floor( regsPerSM / (regsPerThread * threadsRounded(T)) ) bSmem(T) = floor( smemPerBlock / smemBytes(T) ) bHw = maxBlocksPerSM // flat hardware cap // binding constraint = smallest of the four; occupancy uses it in warp terms b(T) = min( bThreads(T), bRegs(T), bSmem(T), bHw ) occupancy(T) = ( b(T) * warpsPerBlock(T) / 48 ) * 100%

TILE_SIZE=32 is bound by raw thread count: blockDim(32,32) = 1024 threads/block, and since 2×1024 > 1536 max threads/SM, only one block can ever be resident — a hard ceiling regardless of registers or shared memory. TILE_SIZE=8 is bound by a different, flatter constraint: the GPU's hardware cap of 16 resident blocks/SM, which becomes binding specifically because 64-thread blocks are small enough that every other resource would allow far more than 16. TILE_SIZE=16 lands in the gap between those two failure modes — small enough that the flat 16-block cap isn't binding, large enough that thread count isn't binding either — leaving registers as the binding constraint, at a noticeably better ratio than either neighbor.

05Key findings

Bigger tiles are not automatically better.

TILE_SIZE=16 beat TILE_SIZE=32 by 15% despite computing a smaller shared-memory tile per block. The bottleneck moved from memory traffic to occupancy, and occupancy is governed by which hardware resource (threads, registers, shared memory, or the flat max-blocks-per-SM cap) binds first — not by tile size alone.

Warp tiling alone did nothing on CUDA cores.

Adding an explicit warp-tile layer between block and thread tiling reorganizes which thread reads which shared-memory address — it creates no new reuse by itself. The best multi-level configuration (5592 GFLOPS) landed within noise of the simpler two-level kernel (5800 GFLOPS). Warp tiling only pays off when paired with something that actually needs warp granularity: bank-conflict-aware layouts, __shfl_sync, or — as it turned out — Tensor Cores.

Tensor Cores were the single largest architectural jump.

Replacing the manual register-accumulation loop with one wmma::mma_sync call per warp lifted throughput from 5800 to 8224 GFLOPS — a structurally different execution path (dedicated matrix-multiply hardware, FP16 inputs, FP32 accumulation) rather than a tuned version of the same CUDA-core kernel.

Double buffering beat higher occupancy.

cp.async double buffering dropped occupancy from 100% to ~67% (two shared-memory buffers instead of one costs registers) yet delivered the largest single gain of the entire investigation — 8224 → 13,358 GFLOPS. Overlapping the next tile's load with the current tile's compute eliminated far more idle time than the occupancy loss cost, a direct counterexample to always maximizing occupancy as a goal in itself.

Empirical tuning beat theoretical prediction, repeatedly.

Every stage that looked like a clear win on paper (bigger tiles, more register reuse, warp tiling) had to be measured to find out whether it actually helped — several didn't. This mirrors how production libraries like cuBLAS and rocBLAS work: an offline empirical search over kernel variants per problem shape, not a single hand-derived "optimal" kernel.

06Remaining gap to cuBLAS

The final kernel reaches roughly 81–95% of cuBLAS. The likely remainder: cuBLAS dispatches between many pre-tuned kernel variants selected per problem shape rather than running one fixed kernel; it likely uses deeper pipelines (3+ pipeline stages vs. this investigation's 2); and portions of its kernels may be hand-scheduled at the assembly (SASS) level in ways standard CUDA C++ can't directly express. Closing that last gap further would mean adopting those same techniques — not a new category of optimization, but a deeper, more exhaustive version of the ones already used here.
