How GEMM Tiling Actually Works

My own working-through of the mechanics behind each optimization in the GEMM project — starting from the two ideas that do the real work (shared memory reuse, register reuse), then what every optimization after that is actually doing.

01Shared memory tiling

The core idea: don't let every thread independently re-read the same data from slow global memory. Instead, one block cooperatively loads a small tile into fast on-chip shared memory once, and every thread in that block reuses it.

Each block owns a fixed TILE_SIZE × TILE_SIZE region of the output C. To compute that region, it needs a full TILE_SIZE-row strip of A and a full TILE_SIZE-column strip of B — but each strip spans the entire width/height N, which is too big to hold in shared memory at once. So the strip gets broken into TILE_SIZE-wide chunks and streamed through shared memory one chunk at a time, accumulating a partial result each pass.

Worked example — N=6, TILE_SIZE=2 (numTiles=3)

Matrix A (6x6)                     Matrix B (6x6)                Matrix C (6x6)
row-strip this block needs:      col-strip this block needs: output tile this block owns:

  t=0  t=1  t=2                   t=0
 ┌───┬───┬───┐                   ┌───┐
 │▓▓▓│   │   │  row 0           │▓▓▓│  col 0                ┌───┬───┬───┐
 │▓▓▓│   │   │  row 1           │▓▓▓│  col 1                │███│   │   │
 └───┴───┴───┘                    ├───┤  t=1                  │███│   │   │
                                   │   │  col 0                ├───┼───┼───┤
                                   │   │  col 1                │   │   │   │
                                   ├───┤  t=2                  │   │   │   │
                                   │   │  col 0                ├───┼───┼───┤

                                   └───┘                       └───┴───┴───┘

Per K-chunk iteration t, every thread in the block cooperatively loads one element of A's chunk and one element of B's chunk into shared memory (As/Bs) — together, the whole block fills the chunk between them. Then, after a __syncthreads(), each thread reads across the whole loaded chunk (TILE_SIZE values) to accumulate its own partial dot product:

// One load per thread, but TILE_SIZE reads per thread once it's in shared memory — // that ratio is the entire reuse win. As[ty][tx] = A[row][t*TILE_SIZE + tx]; Bs[ty][tx] = B[t*TILE_SIZE + ty][col]; __syncthreads(); for (k = 0; k < TILE_SIZE; k++) acc += As[ty][k] * Bs[k][tx]; // TILE_SIZE reads from FAST shared memory __syncthreads(); // before the next chunk overwrites this one
→

The insight: A's tile slides horizontally across K each iteration; B's tile slides vertically. C's output tile never moves — the block just keeps accumulating into it as new chunks stream through shared memory. One global load is reused TILE_SIZE times instead of once, which is the entire source of the 2070 → 2699 GFLOPS jump.

02Register reuse (thread tiling)

Shared memory tiling stopped redundant global reads. Register tiling goes one level deeper: it stops redundant shared-memory reads. Each thread now computes TM output rows instead of 1, accumulating all TM in registers — so a value pulled from shared memory gets reused across multiple output elements by the same thread, not read once and thrown away.

Worked example — TILE_SIZE=2, TM=2 (output tile becomes 4 rows × 2 cols)

Block has 4 threads: (ty,tx) in {(0,0),(0,1),(1,0),(1,1)}

Loading As at tile t (each thread loads TM=2 elements — one per row it owns):
  thread(0,0) loads As[0][0]  ← A[row+0][t*2+0]
  thread(0,0) loads As[2][0]  ← A[row+2][t*2+0]     ← same thread, second row, TM steps apart
  thread(1,0) loads As[1][0], As[3][0]
  ...

Computing (per k): read Bs[k][tx] ONCE, reuse across BOTH of this thread's rows:
  b_val = Bs[k][tx];                 // 1 shared-memory read
  acc[0] += As[ty+0][k] * b_val;      // reused
  acc[1] += As[ty+2][k] * b_val;      // reused again
// acc[TM] lives in REGISTERS, not shared memory — fastest storage on the chip float acc[TM] = {0}; for (k = 0; k < TILE_SIZE; k++) { float b_val = Bs[k][tx]; // read from shared mem ONCE per k for (i = 0; i < TM; i++) acc[i] += As[ty + i*TILE_SIZE][k] * b_val; // reused TM times }
→

The insight: the reuse ratio compounds. Shared memory tiling turned 1 global read into TILE_SIZE shared reads. Register tiling turns each of those shared reads into TM register-level FMAs. This is what pushed CUDA-core throughput from 2699 to 5800 GFLOPS — but only up to a point: more TM means more registers held per thread, which can push occupancy down if taken too far (see the tile-size sweet-spot finding in the main report).

03What the other optimizations are doing

Everything past this point builds on the same two reuse ideas above — reading less, reusing more — just applied to a different resource or a different hardware unit.

Tile-size sweep (8 / 16 / 32)

Occupancy tuning

Not a new reuse mechanism — this is about how many blocks/warps can be resident on an SM at once to hide memory latency. TILE_SIZE sets both the shared-memory tile size and the thread count per block (they're coupled in this kernel), so growing it changes three competing ceilings at once: max threads/SM, max registers/SM, and a flat hardware cap on resident blocks. Whichever ceiling is lowest at a given TILE_SIZE decides the actual occupancy.

Result: TILE_SIZE=16 won — not the biggest tile, the one that avoided every ceiling most efficiently.

Multi-level (block → warp → thread) tiling

Organizational, not reuse

Adds a middle layer: instead of a thread's address being computed directly from the block (blockRow + threadIdx.y), it now goes through an intermediate warp offset (blockRow + warpTileRow + threadRow*TM). This doesn't create new reuse — it's still reading the same shared memory, the same number of times. What it does is give you the vocabulary to know "these 32 threads are in the same warp," which is a prerequisite for a few real techniques: __shfl_sync to swap values between warp threads without touching shared memory, bank-conflict-aware layout of shared memory, or — the big one — Tensor Cores.

Result: on CUDA cores alone, this measured within noise of the simpler two-level kernel. It was necessary groundwork for what came next, not a win on its own.

Tensor Cores (wmma, FP16×FP16→FP32)

Different hardware unit

This is where the warp-tile layer above actually pays off. Instead of a manual register loop doing one FMA at a time, wmma::mma_sync(acc_frag, a_frag, b_frag, acc_frag) is a single instruction that computes an entire 16×16×16 matrix multiply, executed collectively by all 32 threads in a warp on dedicated matrix-multiply silicon — hardware a plain CUDA-core kernel never touches. The tradeoff: inputs must be cast to FP16 (accumulation stays FP32), so there's a small, measured precision cost (~2.4e-3 max error, well inside tolerance).

Result: 5800 → 8224 GFLOPS — the single largest architectural jump in the whole project.

cp.async double buffering

Hiding latency, not adding reuse

Every prior kernel does load → sync → compute → sync, fully serial — nothing starts until the previous step finishes. Double buffering keeps two shared-memory tiles instead of one: while the warp computes on tile t (buffer A), the next tile t+1 is already being copied into buffer B in the background via cp.async, which copies global→shared memory without routing through registers. The two buffers swap roles every iteration.

Result: 8224 → 13,358 GFLOPS, despite occupancy dropping from 100% to ~67% — proof that hiding latency can matter more than maximizing occupancy.

04Tensor Core API & async calls, quick reference

wmma functions

Warp-collective

A fragment isn't a normal array — it's a 16×16(×16) matrix tile whose storage is spread across the warp's 32 threads, hidden from you by the API. All four calls below must be executed by every thread in the warp together — that's what "_sync" means here, not "runs in the background."

fragment<role, M, N, K, dtype[, layout]> // role: accumulator | matrix_a | matrix_b fill_fragment(frag, 0.0f) // zero-init, like acc = 0 load_matrix_sync(frag, ptr, leadingDim) // leadingDim = source array's row stride mma_sync(out, aFrag, bFrag, out) // out = aFrag*bFrag + out, ONE instruction store_matrix_sync(ptr, frag, ld, layout) // mirror of load, writes back to memory

Blocking vs. non-blocking calls

cp.async pipeline

Only two calls in the double-buffered kernel are genuinely non-blocking: __pipeline_memcpy_async (fires the copy, returns immediately) and __pipeline_commit (just closes a batch marker). Everything else — __pipeline_wait_prior, __syncthreads, and all four wmma:: calls above — blocks until it's actually done.

The naming trap: "_async" reliably means non-blocking. "_sync" does not mean the opposite — in wmma/warp context it means "every thread must call this together," and those calls still fully block. Don't infer async vs. blocking from the name alone; check the docs.
